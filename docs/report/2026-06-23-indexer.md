# Relatório: Estabilização do Filesystem Watcher V2

**Data:** 2026-06-23  
**Escopo:** `debouncer.rs`, `indexer.rs`, `ledger.rs`  
**Objetivo:** Resolver os problemas de sincronização do watcher V2 em relação à arquitetura V1, alcançando paridade funcional com o monitor de filesystem estável da versão anterior.

---

## Contexto

O sistema de monitoramento de filesystem (watcher) da V2 utiliza uma arquitetura em três camadas:

1. **Watcher** (`notify` crate) → emite eventos brutos do SO
2. **Debouncer** (`debouncer.rs`) → agrega, filtra e classifica eventos em domínio
3. **Indexer** (`indexer.rs`) → processa eventos de domínio e persiste no banco via Ledger

Na V1, o monitor era síncrono e processava eventos de forma sequencial, o que simplificava a lógica mas limitava a performance. A V2 introduziu processamento assíncrono com heurísticas de detecção de renomeação, mas trouxe race conditions e edge cases específicos do macOS que precisaram ser corrigidos.

---

## Problemas Identificados e Soluções

### 1. Race Condition na Ordem de Processamento do Debouncer

**Problema:**  
O loop principal do `EventDebouncer::tick` processava eventos em ordem arbitrária. Isso causava a emissão prematura de eventos `FsDirectoryDiscovered` (para "Pasta Sem Título") antes que a heurística de renomeação pudesse parear o `delete` + `create` como um `rename`.

**Causa raiz:**  
A fase de "Discovery" (emissão de novos caminhos) executava antes da fase de "Heuristics" (pareamento de renames), gerando duplicatas no frontend.

**Solução:**  
Refatoração do `tick` em três fases sequenciais rigorosas:

```
Phase 1 — Deletions:    Identifica caminhos não-existentes → move para pending_untracked_removes
Phase 2 — Heuristics:   Executa pareamento rename enquanto deletions ainda estão no buffer pendente
Phase 3 — Discovery:    Emite eventos apenas para caminhos que sobreviveram ao pareamento heurístico
```

**Arquivo:** `debouncer.rs` (linhas 198–310)

---

### 2. Heurística de Rename Poluída por Dotfiles do macOS (`.DS_Store`)

**Problema:**  
Ao excluir ou restaurar uma pasta, o macOS automaticamente cria/modifica o arquivo `.DS_Store` na pasta pai. A heurística "Path-only" do debouncer comparava apenas o diretório pai dos caminhos `from` e `to`. Como `.DS_Store` não possui extensão de arquivo, o fallback `is_likely_directory` o classificava incorretamente como diretório, e ele era pareado com o evento de exclusão/criação da pasta real.

**Causa raiz:**  
O fallback "Path-only" não verificava se ambos os lados do par tinham a mesma classificação de diretório.

**Solução:**  
Adicionada verificação `is_likely_directory(&from_path) == is_likely_directory(to_path)` em todos os fallbacks da heurística tardia (Late Heuristic Match), e atualizada `is_likely_directory` para excluir dotfiles:

```rust
// Fallback "Path-only" — agora requer concordância de tipo
} else if from_path.parent() == to_path.parent()
    && is_likely_directory(&from_path) == is_likely_directory(to_path)
{
    // ...
}
```

**Arquivo:** `debouncer.rs` (linhas 389, 437–452)

### 3. Renomeação Case-Only Não Detectada no macOS (`subpasta` → `Subpasta`)

**Problema:**  
O macOS utiliza um sistema de arquivos case-insensitive (APFS/HFS+) por padrão. Ao renomear `subpasta` para `Subpasta`, o Rust (`std::path::Path::exists()`) perguntava ao SO se `subpasta` ainda existia. O macOS respondia `true` (pois `Subpasta` existe e é case-insensitively equivalente), impedindo o debouncer de reconhecer que o caminho antigo havia desaparecido.

**Causa raiz:**  
`Path::exists()` é case-insensitive no macOS, o que mascara renomeações que mudam apenas maiúsculas/minúsculas.

**Solução:**  
Criação da função `path_exists_exact()` que verifica a existência de um caminho com sensibilidade a maiúsculas/minúsculas, enumerando o diretório pai e comparando o nome exato byte a byte:

```rust
fn path_exists_exact(path: &std::path::Path) -> bool {
    if !path.exists() {
        return false;
    }
    
    if let Some(file_name) = path.file_name() {
        if let Some(parent) = path.parent() {
            if let Ok(mut entries) = std::fs::read_dir(parent) {
                while let Some(Ok(entry)) = entries.next() {
                    if entry.file_name() == file_name {
                        return true;
                    }
                }
            }
            return false;
        }
    }
    true
}
```

Substituição de `path.exists()` por `path_exists_exact()` em três pontos críticos do debouncer:
- Confirmação de deletions no guard de 3 segundos (linha 207)
- Classificação de caminhos expirados no buffer (linha 254)
- Verificação de sobrevivência na fase de discovery (linha 277)

**Arquivo:** `debouncer.rs` (linhas 207, 254, 277, 454–476)

### 4. Restauração Rápida Tratada como Move ao Invés de Criação

**Problema:**  
Quando um arquivo era excluído e logo em seguida restaurado (da lixeira ou de volta de uma pasta não monitorada), o `handle_file_discovered` do indexer tentava parear o arquivo restaurado com a exclusão recente via "Fast Match" (comparando `size` + `created_at`). Como o caminho de origem e destino eram **idênticos** (restauração no mesmo lugar), o sistema tratava como um "Move de si para si mesmo", tentava um `UpdateAsset` no banco que falhava (o registro já havia sido excluído), e o arquivo nunca era recriado.

**Causa raiz:**  
A heurística de Fast Match não excluía o caso trivial onde `from_path == to_path`.

**Solução:**  
Adicionada guarda no início do closure de busca em `recent_removals`:

```rust
.find(|entry| {
    if *entry.key() == entry_path {
        return false; // Restauração, não é um move
    }
    // ... resto da lógica de comparação
})
```

**Arquivo:** `indexer.rs` (linhas 537–540)

### 5. Assets de Subpasta Restaurada Aparecendo na Pasta Raiz

**Problema:**  
Ao restaurar uma subpasta contendo arquivos da lixeira, o filesystem emitia um evento de `FsDirectoryDiscovered` seguido de um `scan_directory`. Os arquivos dentro da subpasta eram encontrados pelo scan, porém eram registrados no banco com o `folder_id` da **pasta pai/raiz** ao invés do `folder_id` da subpasta recém-restaurada.

**Causa raiz:**  
O código passava `parent_id` para `scan_directory` ao invés do ID da pasta recém-criada. Ou seja, os arquivos descobertos pelo scan eram associados ao diretório errado.

**Solução:**  
Captura do resultado de `LedgerCommand::CreateFolder` para obter o ID real da subpasta criada, e passagem desse ID para `scan_directory`:

```rust
let create_result = self.ledger
    .execute(LedgerCommand::CreateFolder(CreateFolderPayload { ... }))
    .await;

if let Ok(new_folder_asset) = create_result {
    let _ = self.scan_directory(dir_path, Some(new_folder_asset.id)).await;
} else {
    let _ = self.scan_directory(dir_path, parent_id).await;
}
```

**Arquivo:** `indexer.rs` (linhas 485–500)

### 6. Criação de Nova Subpasta no Finder Não Registrada

**Problema:**  
Ao criar uma nova pasta no Finder, o macOS primeiro cria uma pasta chamada "Pasta Sem Título" e depois a renomeia para o nome digitado pelo usuário. O debouncer corretamente pareava esses dois eventos como um `FsPathRenamed { from: "Pasta Sem Título", to: "nome_real" }`. Porém, no `handle_path_renamed` do indexer, o código buscava a pasta `from` ("Pasta Sem Título") no banco de dados — que nunca havia sido persistida, pois o debouncer consumiu o evento `Created` durante o pareamento heurístico. Como resultado, `find_folder_by_path` retornava `None` e a pasta era silenciosamente ignorada.

**Causa raiz:**  
O `handle_path_renamed` assumia que o caminho `from` sempre existia no banco de dados, o que não é verdade para pastas recém-criadas no macOS.

**Solução:**  
Adicionado branch `else` no `handle_path_renamed` para tratar o caso onde o `from_path` não existe no banco. Nesse cenário, o sistema trata como uma nova criação de pasta usando o caminho `to`:

```rust
if let Some(folder_id) = found_folder {
    // Rename normal: caminho antigo existe no DB
    let _ = self.ledger.execute(LedgerCommand::RenameFolder(...)).await;
} else {
    // Fluxo macOS: "Pasta Sem Título" nunca foi persistida
    // Trata como criação de pasta nova com o nome final
    info!("Indexer: Rename target '{}' not in DB — treating as new folder creation for '{}'", ...);
    
    // Cria a pasta e executa scan para descobrir arquivos internos
    let create_result = self.ledger.execute(LedgerCommand::CreateFolder(...)).await;
    if let Ok(new_folder_asset) = create_result {
        let _ = self.scan_directory(to_path, Some(new_folder_asset.id)).await;
    }
}
```

**Arquivo:** `indexer.rs` (linhas 694–754)

## Decisões de Design

1. **`deletion_guard_duration` de 3 segundos:** Mantido para garantir que renames do Finder (que emitem delete/create em sequência rápida) tenham tempo suficiente para pareamento pela heurística.

2. **`path_exists_exact` como camada de abstração:** Em vez de modificar `std::path::Path::exists()` globalmente, criamos uma função dedicada que é usada apenas nos pontos onde a sensibilidade a maiúsculas/minúsculas é crítica (debouncer). Isso evita overhead desnecessário em outros contextos.

3. **Fallback conservador em `handle_path_renamed`:** Quando o `from_path` não existe no DB, o sistema assume que é uma criação de pasta nova (fluxo macOS) ao invés de silenciosamente ignorar. Isso garante que novos diretórios são sempre registrados.

4. **Guarda `from == to` no Fast Match:** A checagem é feita no início do closure para evitar qualquer overhead de comparação de metadados quando o caminho é idêntico (caso de restauração).

## Observações sobre Warnings Residuais

Os logs ainda podem exibir warnings de "Normalization mismatch" em cenários onde:
- Um asset é movido para uma subpasta e, em seguida, o debouncer emite um delete tardio para o caminho antigo (que já foi atualizado no DB via Move)
- O caminho antigo não existe mais no banco porque o `UpdateAsset` já o atualizou

Esses warnings são **benignos** — indicam que o sistema tentou deletar um registro que já havia sido corretamente movido. O asset permanece íntegro no banco com seu caminho atualizado. Os warnings servem como indicador de que eventos duplicados do SO foram corretamente ignorados.
